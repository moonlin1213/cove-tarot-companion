# cove-tarot-companion：原生三平台支持设计

日期：2026-09-01。状态：设计已获用户口头批准，等待书面规格复核后进入实施。

## 1. 目标

在不改变 Tarot Ritual 原有 provider、模型、提示词、解读协议和占卜体验的前提下，让 `cove-tarot-companion` 原生支持：

- Windows 10/11 x64；
- macOS Intel 与 Apple Silicon；
- Linux x64。

Windows 用户应当能直接在 PowerShell 或普通命令提示符中安装、诊断、启动、更新和卸载，不依赖 WSL、Git Bash、Docker、Python或需要本地编译的 npm 原生扩展。macOS 与 Linux 的已有安装和数据不得因本次适配发生迁移、重置或行为变化。

本次不承诺 Windows ARM、移动平台、GUI 安装器、系统级自动更新器或开机常驻服务。Windows ARM 可以在纯 Node.js 能力恰好可用时尽力运行，但不列入发布验收和支持声明。

## 2. 核心原则

跨平台差异集中在一个很薄的系统适配边界中；业务层仍使用统一接口。邀请额度、同意流程、会话与结果持久化、原解读转交、Skill 行为和宿主合同不按操作系统分叉。

新增 `src/platform.mjs`，负责以下能力：

1. 选择默认私有数据目录；
2. 创建并验证私有目录与敏感文件；
3. 规范化、比较并确认路径包含关系；
4. 解析平台命令名称，例如 Windows 的 `npm.cmd`；
5. 启动、隐藏和停止本程序拥有的子进程；
6. 为安装器提供平台安全的替换、重试和清理语义。

`src/config.mjs`、`src/engine.mjs` 和 `scripts/install.mjs` 通过该模块使用平台能力，不在各处散布 `process.platform === "win32"`。允许入口层根据平台选择文案或默认路径，但安全判断必须只有一个实现来源。

不引入新的模型工具、不创建第二套 provider 设置、不复制或转换用户凭据、不修改上游 Tarot Ritual 的模型选择和解读实现。

### 2.1 方案取舍

采用“薄平台适配层”而不是以下方案：

- 不在 `config`、`engine`、安装器和 CLI 中分别堆叠 Windows 条件分支；这种方式改动看似更少，但权限、路径和进程规则会迅速分散，难以证明三个平台遵守同一安全合同。
- 不维护独立 PowerShell/Bash 安装器；三套安装实现容易产生版本固定、回滚和自定义文件保护差异。
- 不引入原生 ACL/进程 npm 扩展；它们会增加架构相关二进制、供应链和安装编译问题，与本项目纯 Node.js 的可携带性目标相冲突。

平台适配层让各操作系统使用自己的安全原语，同时让上层获得相同的成功、拒绝和错误结果，是兼容性、可审计性与维护成本之间最常规的平衡。

## 3. 数据目录与向后兼容

### 3.1 默认目录

- macOS 和 Linux：继续使用现有 `~/.local/share/cove-tarot-companion`，不迁移已有安装。
- Windows：使用 `%LOCALAPPDATA%\cove-tarot-companion`。

显式 `--data-dir` 在三平台继续可用。所有内部路径都使用 Node `path` API 构造；公开文档不要求用户手工拼接分隔符。

Windows 缺失或无法解析 `LOCALAPPDATA` 时，程序不得猜测公共目录或当前工作目录，应给出明确错误并提示使用 `--data-dir` 指定本机私有目录。

### 3.2 路径身份与包含关系

路径校验必须处理：

- Windows 盘符大小写与文件名大小写不敏感；
- `/` 与 `\` 的平台差异；
- 空格、中文及其他 Unicode 字符；
- 短路径、符号链接、junction 和其他 reparse point；
- 同名但不相同的路径前缀，例如 `data` 与 `data-copy`；
- 安装目标和数据目录互相嵌套导致更新或卸载误删的情况。

包含判断以解析后的路径组件和实际文件身份为准，不能使用字符串 `startsWith`。安装器拒绝把代码目录、数据目录、Skill 目录放入会让更新、回滚或卸载越界的关系中。

默认只支持本机文件系统上的私有数据目录。Windows UNC、设备路径和映射到无法验证 ACL/原子替换语义的网络位置应在写入凭据或切换代码前拒绝，并给出可操作的本地目录建议。

## 4. 私有权限与文件安全

### 4.1 macOS/Linux

保留现有 Unix 防护：私有目录与文件的 owner、mode、普通文件类型、符号链接规避和 `O_NOFOLLOW` 检查。目录使用仅当前用户可访问的权限，敏感文件使用仅当前用户可读写的权限。

### 4.2 Windows

Windows 不把 Unix mode 位当作安全保证。平台层使用 Windows 自带能力检查并收紧目录 ACL，目标是：当前登录用户和操作系统管理主体可访问，普通其他用户与继承来的宽泛写权限不应访问连接密钥、状态数据库或 provider 相关运行数据。

实现优先使用系统自带 PowerShell/.NET ACL 接口或 Windows 命令，不增加需要编译的第三方原生依赖。调用必须通过参数数组或安全编码的脚本输入传值，不能把路径插入可执行命令字符串。

安全流程为：创建私有根目录，停止危险权限继承或写入专用 ACL，重新读取并验证有效 ACL，然后才生成授权密钥、数据库或运行状态。验证失败时保持失败关闭，不降级为公开可写目录，也不在日志中打印密钥内容。

现有目录如果包含 symlink、junction 或无法判定的 reparse point，程序必须在写入敏感数据前拒绝。普通代码资源可以读取，但任何会被更新器替换或卸载器删除的目标也必须先确认没有逃出受管根目录。

## 5. 安装、更新与卸载

保持一个 JavaScript 安装器和一个 CLI，不为三平台维护三套不同业务流程。

### 5.1 命令解析

- POSIX 使用 `npm`、`node`、`git` 等普通可执行名称；
- Windows 根据 Node 的进程启动规则使用 `npm.cmd`，并正确处理 `.cmd`/`.bat` 入口；
- 所有子进程使用参数数组和 `shell: false`；只有 Windows 对批处理入口确实需要系统命令解释器时，才使用受控包装，且所有用户路径仍作为独立参数传递；
- 不修改系统 PATH，不安装全局 npm 包，不静默安装 Node 或 Git。

安装器继续固定公开 Tarot Ritual 的 40 位 commit，使用 lockfile 安装依赖，先在受管 staging 目录完成验证再切换。Windows 上针对文件扫描器、索引器或浏览器短暂占用文件的常见情况允许有限、带截止时间的重试；不得无限循环，也不得因失败删除旧的可用版本。

### 5.2 幂等与保护

重复安装、明确更新和代码卸载的既有合同保持不变：

- 不覆盖用户修改的受管文件；
- 不覆盖自定义牌面；
- 更新失败保留旧代码和全部数据；
- 普通卸载只删除已确认归本安装管理的代码；
- 清除用户数据仍需单独明确确认；
- Windows 大小写别名、junction 和占用文件不能绕过受管文件清单。

若原子目录替换在目标文件系统上不成立，安装器必须在切换前中止，而不是进行可能留下半套版本的逐文件覆盖。

## 6. 服务与子进程生命周期

本地服务仍只绑定 loopback，不新增公网监听或云中转。三平台均按需启动，不默认创建开机自启项。

平台层启动子进程时：

- 保留现有代理环境与原引擎命令行参数；
- Windows 设置 `windowsHide: true`，避免每次解读弹出控制台窗口；
- 记录本程序实际启动的子进程句柄、PID 和实例身份；
- 健康检查必须确认协议与安装身份，端口被无关程序占用时拒绝接管；
- 永远不通过“找到占用某端口的 PID”来猜测并终止进程。

停止流程只作用于本实例拥有的进程。POSIX 保留当前优雅信号与有限强制终止流程；Windows 使用 Node/系统可验证的进程终止能力，并处理进程已退出、PID 重用和子进程树残留。升级或卸载若不能证明目标属于当前安装，应停止并报告，而不是强制结束未知程序。

服务异常退出、电脑重启或浏览器关闭后，数据库中的抽牌、揭示和已接受解读仍按现有恢复协议处理；跨平台适配不得新增自动付费重试。

## 7. 用户体验与文档

README 和 README.en.md 分开提供：

- macOS/Linux 的 Bash 安装、诊断、更新与卸载示例；
- Windows PowerShell 的等价原生命令；
- Node.js 24.5+、Git 和本地浏览器等前置条件；
- 默认数据目录和 `--data-dir` 用法；
- Windows 不需要 WSL 或 Git Bash 的明确说明；
- 当前正式支持的平台与不在承诺范围内的平台。

PowerShell 示例必须可直接复制，不混用 Bash 的续行符、环境变量语法、`~` 假设或 `/tmp`。错误信息应使用用户输入的安全显示路径说明问题，但不得输出授权 token、provider 凭据、请求正文或完整敏感配置。

Skill 的触发、邀请和结果读取说明保持平台中立；只在需要执行本地命令的参考文档中列出平台差异。

## 8. 错误处理

以下情况必须在写入凭据、启动引擎或切换代码之前失败关闭：

- 私有目录权限无法建立或复验；
- 数据目录位于不支持的网络、设备或不可靠文件系统；
- 目标路径越出受管根目录或经过无法判定的链接/reparse point；
- Node、npm、Git 或固定引擎版本无法可靠解析；
- staging 验证失败或无法安全替换旧版本；
- 目标端口已有身份不符的服务；
- 无法证明待停止进程由本实例拥有。

失败信息包含：发生在哪个阶段、没有执行哪些后续动作、原版本和用户数据是否仍安全、用户可以运行的诊断命令。临时文件占用只进行有上限的重试；鉴权、版本、路径身份和权限错误不盲目重试。

## 9. 测试策略

GitHub Actions 使用原生矩阵：

| 平台 | Runner | 必须覆盖 |
| --- | --- | --- |
| Linux x64 | `ubuntu-latest` | 现有完整套件、Unix 权限、Chromium/WebKit、安装生命周期 |
| macOS Intel | 当前可用的 GitHub Intel 原生 runner | 现有完整套件、Unix 权限、安装生命周期、浏览器流程 |
| macOS Apple Silicon | 当前可用的 GitHub arm64 原生 runner | 现有完整套件、Unix 权限、安装生命周期、浏览器流程 |
| Windows x64 | `windows-latest` | PowerShell 安装、ACL、大小写路径、进程生命周期、Edge/Chromium、更新卸载 |

工作流实现时依据 GitHub 官方当前 runner 清单选择具体 macOS 标签，并通过 `process.arch` 断言任务确实分别运行在 `x64` 与 `arm64`，不能用模拟架构或 Rosetta 任务代替原生验收。

公共发布门禁必须覆盖：

1. 空目录原生安装、重复安装、明确更新、代码卸载和保留数据；
2. 从公开仓库安装清单中固定的真实 Tarot Ritual commit；
3. 带空格与中文的代码、数据和 Skill 路径；
4. 大小写差异、相似路径前缀、symlink/junction/reparse point 逃逸；
5. Unix owner/mode 与 Windows ACL 的成功和失败关闭；
6. 本程序拥有的后端正常停止、超时停止、已退出和端口被无关服务占用；
7. 电脑重启等价的冷启动恢复、抽牌记录、原解读回传和未知解读不重试；
8. 自定义牌面、状态、邀请额度与 provider 行为在更新前后不变；
9. README 中各平台复制命令的自动化冒烟验证；
10. 原 Skill 格式、去个人化扫描、许可证和固定上游版本检查。

平台专属安全测试不得以 skip 通过。某平台无法执行发布门禁时，该平台不能被 README 或 release 标记为正式支持。

真实 provider 凭据不进入 CI；模型请求继续使用隔离的本地假服务。真实浏览器验收验证界面与桥接，不用于证明所有第三方模型供应商可用。

## 10. 发布与回归边界

实现按测试驱动顺序进行：先为平台接口和 Windows 差异补失败测试，再改生产代码；随后运行各平台矩阵和公开安装验收。macOS/Linux 现有完整测试必须继续通过，不能用平台判断跳过已有断言。

发布声明只在三平台原生任务全部通过后更新。若 Windows 实现完成但矩阵尚未通过，文档只能标为预览，不得提前写“原生支持”。

本次变更不得修改：

- Tarot Ritual provider 列表、默认选择和导入规则；
- OAuth/DSH/自定义 provider 语义；
- 模型名称、temperature、max tokens 或提示词；
- 抽牌、整组翻牌、缩放、解读展示和结果摘要合同；
- 主动邀请每天滚动 24 小时最多 3 次及拒绝冷却；
- 用户自定义牌面与本地记录的所有权。

## 11. 设计自审

该设计将操作系统差异限制在路径、权限、命令和进程四类能力中，没有复制业务逻辑，也没有借跨平台适配重新设计占卜引擎。Windows 采用系统原生 ACL 和 PowerShell 能力，不要求兼容层；macOS/Linux 保留原数据位置和 Unix 防护，避免迁移风险。

安全策略在无法验证时停止，代价是部分网络盘和复杂企业目录不会被首版支持；这比把授权密钥写入无法证明私有的目录更符合本地陪伴系统的边界。通过原生 CI、真实公开安装、Unicode/空格路径和平台安全测试，可以把“代码理论上可运行”与“正式原生支持”区分开。
